# 内嵌智能体规范（员工语音/文字在 ERP 内干活）

> 版本：v1（初稿）
> 更新日期：2026-10-22
> 说明：规定 ERP 内嵌智能体的模型网关、交互形态、权限关联、开源框架接入方式。与《API文档规范.md》《开发规范.md》配套。核心立场：**智能体是员工权限的放大器，不是越权通道。**

---

## 一、定位

员工在 ERP 的智能体对话界面，**用文字或语音**发起业务动作（查库存、开裁剪单、报工、看看板……），智能体解析意图 → 校验该员工权限 → 调 ERP 能力 → 结果回显（可 TTS 播报）。智能体不是新系统，是**该员工操作入口的另一种形态**。

---

## 二、模型网关（LLM / TTS / ASR 三类，均走 OpenAI 协议）

1. **三类模型统一走 OpenAI 兼容协议**（`/v1/chat/completions`、`/v1/audio/speech`、`/v1/audio/transcriptions` 或厂商对应端点）：
   - **LLM**：意图理解 + 能力编排（对话大脑）
   - **TTS**：把智能体回复/关键结果念出来（语音合成）
   - **ASR**：把员工语音转成文字（语音指令入口）
2. **每类支持配置多套**（同名多实例，按后缀区分），界面可切换"用哪套"，不写死一家。
3. **密钥只进 `.env`，不进数据库、不进 Git**：
   - `.env` 里按类别放多组：`LLM_1_API_KEY` / `LLM_1_BASE_URL` / `LLM_1_MODEL`，`TTS_1_*`，`ASR_1_*`
   - `.env` 必须进 `.gitignore`；仓库只提交 `.env.example`（占位符模板，不含真实 key）
   - 界面**只选"用哪套已配置网关"，不提供填 key 的入口**（避免 key 落库/落前端）
   - 数据库里的 `sys_config` 存"网关选择、模型名、温度"等**非密钥**配置即可（沿用旧项目 agent.* 思路，但 key 一律挪走）

---

## 三、交互形态与语音链路

1. **对话界面**：ERP 内置一个智能体会话页，文字输入 + 语音输入/语音输出。
2. **语音链路放前端直连网关**（不录整段音频往后端转）：
   - 前端调 ASR 网关：员工语音 → 文字
   - 文字作为普通指令进后端（后端只见"文字意图"，逻辑清晰、好留痕、好做权限）
   - 前端调 TTS 网关：智能体回复文本 → 语音播报
   - **后端介入的三个点（必须留痕 + 校验）**：员工说了什么（意图原文）、解析成哪个动作、结果是什么
3. **文字优先、语音是增强**：语音识别失败/无语音时，界面退化为纯文字输入，功能不受影响。

---

## 四、权限关联（强制，安全红线）

1. **智能体每次写操作，以发起员工本人的身份执行**：操作日志里"操作人"记员工工号，**不记"AI/智能体"**，保证可追责。
2. **可执行动作集 = 该员工角色权限过滤后的 MCP 工具集**：无权限的动作在对话里**直接不出现**（不是出现了点了报"无权限"——后者体验差且泄露功能存在性）。
3. **禁止越权通道**：智能体不得调用超级管理员/系统级权限代执行。任何"为了好用给智能体开个万能口子"的设计，一律拒绝。
4. 读操作同样按该员工的数据权限范围过滤（看得到自己该看的，看不到别人的）。

---

## 五、开源 Agent 框架接入（"壳"不是"钥匙"）

1. **允许拉一个开源 agent 框架做内嵌对接**（做对话管理、工具调用编排的壳），但它是**壳**，不是能力本身。
2. **框架调用的"工具"只能是我们自己定义的 MCP 工具 / 面向动作 API**，不得让框架直接连数据库、不得绕过权限层。
3. 选型前定死三条红线（选任何框架都要过）：
   - 能接入**自定义 MCP 工具**（不是只认它内置的工具）
   - 支持**按调用方身份动态过滤工具集**（对应第四节权限关联）
   - 框架自身**不内置直连数据库**的默认行为（否则会拿到万能钥匙）
4. 框架进仓库前登记：用的哪个框架/版本、接了哪些自定义工具、权限怎么接的，写进《开发日志.md》。

## 六、知识库与向量检索（RAG）

> 定位：内嵌智能体回答业务问题前，先检索厂内知识再答，不靠 LLM 通用知识瞎编。知识源 = Docs/知识库/（唯一事实源），向量库只是"影子索引"。

### 6.1 配置（全部走 .env，禁止写死）
- `EMB_BASE_URL` / `EMB_API_KEY` / `EMB_MODEL` / `EMB_DIM=1024` / `EMB_MAX_TOKENS=512`
- 开发测试环境：本地/内网 LM Studio（bge-large-zh-v1.5，端点 127.0.0.1 或内网机器占位，真实值只在 .env 填）
- 换环境/换 embedding 模型（维度变）只改 .env；维度变了必须重建向量库（Chroma 向量空间不通用）
- **红线：任何 base_url/密钥/模型名/维度不得写进代码、SQL、文档的可运行值**

### 6.2 向量库
- 用 **pgvector（建在主库 PostgreSQL 里）**——零额外组件/零额外故障点，最省；技术栈定稿 2026-10-23 由 Chroma 改为 pgvector
- 切片粒度 = 一条知识一区块（见《知识库索引.md》），**单条 ≤400 汉字**（BGE 上限 512 token ≈ 500 汉字，留余量）；超长拆条用"原文ID+序号"关联
- 每切片带元数据：类别/款号/工序/客户/更新日期，支持条件过滤检索
- 知识文档是事实源；文档变更 → 跑 `重建索引.py` 重建，向量库不同步就作废

### 6.3 检索与降级
- 智能体回答：员工提问 → 向量检索 top-k（带元数据过滤）→ 片段拼进 LLM 上下文 → 回答
- **降级路径（必做）**：`EMB_FALLBACK_FULLTEXT=1`，向量端点不可达 → 回退"知识库全文直读"（把相关文件整段喂 LLM），避免"向量库挂=智能体不能答"
- 检索不到（相关度低于阈值）→ 不硬答，转人工

### 6.4 向量库模型指纹与自动作废（防换模型/换地址后向量库静默报废）

- **指纹 = `EMB_MODEL + EMB_DIM + EMB_MAX_TOKENS`**，写入 Chroma 集合元数据（跟向量库走，不跟环境/代码走）。
- 程序**每次启动 / 每次检索前**校验：用当前 `.env` 的三项算指纹，与库内指纹比对。
  - 一致 → 正常检索。
  - 不一致（换了模型或维度）→ 旧向量库判定作废，按 `REBUILD_ON_MODEL_CHANGE` 开关处理：
    - `auto`：启动时自动全量重建（跑 `重建索引.py`）再检索。
    - `warn`：报警"向量库与当前模型不匹配"，临时退回全文直读降级，等人工手动重建。
- **运维含义**：生产换地址/换模型 = 只改 `.env` 的 `EMB_*` + 重启，代码一行不改；系统按指纹自己决定重建还是降级。杜绝"换完模型检索全乱还没人发现"。

### 6.5 两期节奏
- **第一期（开发测试期跑通）**：Chroma 单文件 + 手动 `重建索引.py`（调 .env 的 EMB 端点）+ 检索 top-3 + 端点不可达降级全文直读。链路完整、量小、可演示"员工问→检索/降级→回答"
- **第二期（知识堆多/上生产）**：文档变更自动重建、元数据复杂过滤、相关度阈值、向量端点健康监控；量级真大/要独立向量服务时，再评估迁 Milvus（embedding 走 OpenAI 协议，换库只换存取层，不重算）

## 六、落地节奏

1. 本文档先定（技术栈无关）。
2. 技术栈落地后：建 `.env` + `.env.example` + 三类网关配置读取层（复用旧项目 `agent_client.py` 的 OpenAI 兼容客户端思路，扩成多类多套）。
3. 按《API文档规范》生成全量"面向动作 API + 机器契约"，封装成 MCP 工具。
4. 选开源框架做对话壳，接 MCP 工具 + 权限过滤 + 前端语音链路。
5. 每个被智能体接管的动作，补"权限 + 留痕"测试（该员工无权限时应看不到/不可执行该动作）。
