# 多人协作与任务交接

> 本文件是团队角色、任务拆分、分支、PR、评审、集成和发布交接的唯一规范来源。编码、文件头、数据库和测试细则见《开发规范》；单个功能的记录使用《功能任务模板》。

## 一、角色与责任

| 角色 | 主要责任 |
|---|---|
| 业务负责人 | 确认业务目标、会改变业务结果的规则和用户验收结论 |
| 任务负责人 | 拆分范围和子任务，确定依赖，协调共享契约，跟踪交付证据、遗留项和文档状态 |
| 实施人员 | 按已确认契约完成代码/文档/迁移，维护文件头，执行适用验证并记录真实结果 |
| 评审人员 | 独立检查业务边界、实现质量、权限、数据、迁移、安全和测试证据 |
| 测试人员 | 按验收场景记录测试环境、测试时间、测试人员、结果和缺陷；可与实施人员不同 |
| 发布负责人 | 确认目标分支与环境、变更清单、迁移、备份恢复、冒烟和回退方案 |

小团队可以由一人承担多个角色，但 PR 作者不能作为该 PR 的独立批准人。用户业务验收、代码评审和生产发布是不同责任，不能相互替代。仓库维护者应维护模块/目录与责任人映射（可使用 `CODEOWNERS`）；映射尚未建立时，任务记录必须明确指定评审人和发布负责人。

## 二、任务进入开发

任务负责人为每项可验收功能建立一份任务记录，使用《功能任务模板》。至少明确：

- 任务编号、业务目标、用户角色、范围、不做内容、负责人、参与者和验收人。
- 业务规则来源、关键场景、异常与权限边界、验收条件及风险。
- 涉及模块、页面、API、权限、数据表、文件、配置和外部服务。
- 前置依赖、共享文件/接口/表、契约负责人、唯一 DDL 负责人和并行工作包。
- 目标集成分支、PR 依赖关系、验证环境、计划执行的检查和待决策事项。

用户确认业务目标与关键规则并授权实施后，负责人可自主决定一般技术实现和文件拆分。涉及业务结果歧义、权限/审批规则变化、授权范围外模块、重要数据不可逆影响、生产操作或明显外部成本时，先提出有影响说明的决策项，并继续推进不依赖该决策的工作。

## 三、并行开发与共享契约

1. 一个需求由一名任务负责人统筹；每个子任务有唯一负责人、交付物、依赖和验收条件。
2. 前后端、数据库、报表或其他模块并行前，先确认 API 请求/响应、错误、状态流转、权限、数据范围和数据库字段契约。契约可先通过任务记录冻结并指定负责人；后续变更须通知所有依赖方并更新版本/记录。
3. 同一张共享表或同一迁移批次只指定一名 DDL 负责人。其他人员基于确认的契约开发，不各自编辑同一迁移。
4. 每人使用独立分支和 Git worktree，不共用工作目录、不覆盖他人未提交内容。提交仅包含本任务相关内容。
5. 任务拆分按可独立评审、可验证的工作包进行，不按“改几个文件”机械拆分。PR 依赖未合并分支时须写明依赖和合并顺序。

## 四、分支与集成

1. 团队使用一个由维护者确认并记录的集成目标。`dev` 仅在远端确实建立且保护规则配置后启用；未建立时按已确认的集成策略执行，不得自行假设存在 `dev`。
2. 每个任务从当前约定的集成分支创建 `feat/<功能>` 或 `fix/<缺陷>` 分支；建议使用简短、易搜索的名称。PR 目标分支必须与仓库实际保护配置和项目记录一致。
3. `main` 和已配置的集成分支禁止直接推送、强推和绕过保护。维护者须为远端分支配置必要的评审和自动检查，并让仓库设置与本规范一致。
4. 合并冲突由相关任务负责人协调；涉及共享数据库迁移时由 DDL 负责人统一整理。不得通过强制覆盖公共分支处理冲突。

## 五、PR、评审与合并门槛

PR 描述必须提供：

- 关联任务编号、需求来源和实际行为变化。
- 改动文件/模块及责任人；API、数据库、权限、配置、文件和外部依赖影响。
- 文件头是否已更新；迁移执行顺序、兼容性、验证和恢复/补偿方法。
- 实际执行的构建、测试和手工验收步骤、环境、时间、人员、结果及证据；未执行项和原因。
- 截图或日志（适用时，须脱敏）、依赖 PR、遗留事项和后续任务。

多人团队至少一名非作者评审并批准；涉及权限、安全、数据库共享结构、财务计算或公共接口时，由对应模块负责人参与评审。已配置的构建、静态检查和相关自动化测试必须通过；自动检查未配置时，提交实际命令和结果供评审核对。PR 检查按改动范围执行，完整回归作为发版门槛，不要求每个 PR 无差别执行所有慢速检查。

评审应检查需求和实现一致、业务边界和错误行为完整、前后端权限均正确、数据范围和审计可靠、迁移安全、文件头/文档与实现一致、测试覆盖验收条件、无凭据和个人敏感信息。作者根据意见修改后，由评审人确认解决再合并。

## 六、验收、发布与交接

1. 用户验收只覆盖其确认的具体版本和场景；开发团队评审和 CI 不能代替用户业务验收。
2. 功能合并前，任务负责人确认任务记录、迁移、权限、审计、API/MCP/Skill 文档、文件头、测试证据和遗留事项齐全；只更新本次实际影响的功能状态。
3. 发布负责人在发布前核对目标版本和环境、迁移顺序、备份/恢复、发布后关键流程冒烟及回退方案。生产部署或生产数据库变更须取得项目授权后执行。
4. 合并完成后，负责人更新《功能实现状态》、模块文档和任务记录；未完成事项转为有负责人和状态的后续任务。
5. 交接说明至少包含当前状态、代码/PR、数据库版本、部署配置影响、已验证/未验证范围、已知风险、运行排障线索和下一责任人。

## 七、任务节奏

需求与验收条件明确 → 任务和角色登记 → 共享契约冻结 → 独立分支/worktree 并行实现 → PR 独立评审和自动检查 → 集成环境回归 → 用户验收 → 发布检查与版本记录 → 遗留事项交接。
