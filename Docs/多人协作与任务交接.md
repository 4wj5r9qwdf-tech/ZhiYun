# 多人协作与任务交接

> 版本：v1（按功能任务协作）
> 更新日期：2026-11-02
> 说明：规定多人并行开发织云 ERP 时的任务拆分、代码隔离、接口/数据库协作、评审与验收交接。与《开发规范.md》《功能实现状态.md》《测试与验收清单.md》配套。

---

## 一、协作原则

1. **一个需求有一个负责人**：负责人对需求澄清、任务拆分、跨端联调、测试证据和交接完整性负责；子任务可分配给不同开发者。
2. **按可验收功能拆分**：每个任务有明确输入、输出、边界和验收条件，避免按“改几个文件”拆成无法单独验证的任务。
3. **先定共享契约再并行**：前后端、数据库、报表或其他模块有依赖时，先确认字段、API、权限、状态流转和错误行为，再安排并行实现。
4. **每人独立分支和工作区**：不得多人共用同一工作目录或互相覆盖未提交改动。推荐每个任务一个 Git 分支和独立 worktree。
5. **文档是交接依据，Git/PR 是变更载体**：需求、实现确认、接口/DDL 契约、验收和遗留事项写入仓库文档或 PR；口头消息不作为唯一交接记录。
6. **数据库变更指定唯一责任人**：同一张表/同一迁移批次只设一个 DDL 负责人，其他开发依赖已确认的字段契约，不各自修改同一份迁移。

## 二、任务进入开发前

任务负责人建立任务说明，至少包含：

- 任务编号、功能名称、负责人、参与人、目标分支。
- 业务目标、用户角色、范围与明确不做的内容。
- 所属模块文档和功能命名清单条目。
- 页面、API、权限、数据库和外部服务的影响范围。
- 依赖任务、共享文件/表/API，以及由谁维护共享契约。
- 验收条件、正向/异常/权限/边界场景和验收人。
- 当前阻塞、风险和待用户确认事项。

开工前仍须遵循《开发规范.md》功能开发流程：先与用户确认需求与实现方法、字段和影响面，再开始代码实现。该文档不替代用户确认。

## 三、并行任务拆分

推荐拆分为可独立审查的工作包：

| 工作包 | 主要交付 | 并行前置条件 |
|---|---|---|
| 数据契约/DDL | 表字段、索引、约束、迁移与回滚说明 | 字段和状态流转已确认；指定唯一 DDL 负责人 |
| 后端 | API、校验、权限、业务事务、后端测试 | API/数据契约已确认 |
| 前端 | 页面、交互、请求适配、前端校验 | API 请求/响应与错误约定已确认；遵循《前端规范.md》组件库及页面模板 |
| 测试与验收 | 场景、测试数据、回归范围、结果记录 | 验收条件明确；测试环境可用 |
| 文档 | 需求、功能状态、API 契约、操作说明 | 以已确认方案和实现/实测为依据 |

可按前后端并行开发，但共享契约必须先合并或由任务负责人冻结并引用版本。未确定的字段不得由前端和后端各自假设。

## 四、代码分支与集成

1. 每个任务从团队约定的集成分支创建独立 `feat/<功能名>` 或 `fix/<缺陷名>` 分支；若项目尚未建立 `dev` 分支，先由维护者确定集成分支，不要自行假设。
2. 每个开发者在独立本地分支/worktree 工作，提交只包含该任务所需变更。
3. 子任务可分别提 PR；若依赖未合并的前置分支，PR 必须写清依赖关系和预期合并顺序。
4. 合并冲突由冲突文件的负责人协调解决；数据库迁移冲突交由指定 DDL 负责人统一整理。
5. 不直接向 `main` 推送，不强制覆盖公共分支历史。合并规则以《开发规范.md》Git 规范为准。

## 五、PR 交接内容

每个 PR 描述必须说明：

1. 关联任务和需求文档位置。
2. 实际行为变化、明确未覆盖内容。
3. API、数据库、权限和配置影响；没有影响也要注明。
4. DDL/迁移执行顺序及是否需要回滚。
5. 执行过的构建、测试和手工验收步骤及结果；未执行项与原因。
6. 截图或日志证据（适用时），不包含凭据和个人敏感信息。
7. 遗留问题、后续任务、依赖 PR。

评审重点：业务边界与确认方案一致、权限/数据范围正确、DDL 可追溯、测试覆盖验收条件、文档与实际行为一致、无敏感信息。

## 六、完成与状态交接

合并前由任务负责人确认：

- [ ] 需求文档与实现一致，用户要求的方案确认已记录。
- [ ] 相关构建和测试完成，测试结果附在 PR 或验收记录。
- [ ] DDL/配置/权限变化已说明，迁移脚本已纳入版本控制。
- [ ] API 文档仅记录真实实现并经接口核对；智能体契约按项目范围和用户确认执行。
- [ ] 更新《功能实现状态.md》、模块文档和开发日志中与本次任务有关的部分。
- [ ] 遗留事项已转为独立任务并指定负责人或标记阻塞。

具体业务验收仍由用户完成；开发团队内部评审不能代替用户验收。

## 七、推荐的协作节奏

1. 负责人将需求拆成任务并建立任务说明。
2. 先确定 API/DDL 等共享契约和任务依赖图。
3. 开发者在独立分支/worktree 并行实现。
4. 各工作包分别 PR 评审，按依赖顺序合并到集成分支。
5. 在 WSL/Ubuntu 集成环境运行回归并记录结果。
6. 负责人汇总变更与遗留项，组织用户验收。

## 八、任务说明模板

使用同目录的《功能任务模板.md》为每个功能建立任务说明；任务完成后保留交接记录，长期未采用的任务草案可归档，不要把多个功能的状态混写在开发日志中。
