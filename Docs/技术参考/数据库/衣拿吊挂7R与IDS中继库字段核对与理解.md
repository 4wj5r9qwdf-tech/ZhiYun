# 衣拿吊挂 7R 与 IDS 中继库字段核对与理解

> 文档版本：2.1；更新日期：2026-11-25。本文记录已由文档、SQL、客户端副本静态证据和客户端页面截图支持的结论，并明确标出仍需配置页/厂商核实的内容。

## 1. 结论摘要

1. `7R标准公共数据库对接字典说明V2.0.xlsx` 是一份通用对接说明，描述 ERP/MES 与衣拿之间可采用的下发和回传结构；它还明确区分“每条产线数据库”和“INA Server 汇总库”两种部署方式，并提示两种方式需要不同的对接软件。用户补充确认：当前吊挂数据上传到中继库由独立客户端工具负责配置；因此文档定义的对象在本地库中不存在或没有同步记录，应优先判断为客户端尚未配置上传，而不是直接判断软件版本不支持。
2. `IDS视图字段说明-20241223.xlsx` 是带日期的 IDS 视图字段参考。它能帮助理解 2024-12-23 文档所描述的三个视图，但不能替代当前 IDS 数据库的系统目录和真实视图定义。
3. 本次检查的 SQL Server `IDS` 数据库中，实际看到 7 张相关下发基础表和 3 个回传视图。下发端有单独的颜色、尺码基础表；当前 IDS 没有与 7R `Tag_Info` 同名的对象，但有内部 `P_Barcode_Info` 表。用户提供的本机 DataThreadSync 副本代码包含从线体 `Barcode_Info` 同步至 `P_Barcode_Info` 的特殊路径，副本配置开关为 `false`；这不是实际运行机器的启用状态，也不能证明内部表和 7R `Tag_Info` 完全等价。用户提供的运行客户端主页面截图显示 1–5 号线的 IHS/IHS_SHARED 连接已启动、6 号线两条连接异常；日志可见 Hanger_Master、Hanger_Routing_Details、ODP_Master、ODP_Detail 的上传记录。随后提供的数据库设置截图揭示了按线体分别配置 `IHS`/`IHS_SHARED` 源库、源表名、服务器表名及查询语句的机制，并给出 1 号线两库的部分表映射样例；用户确认各产线常规映射规则相同，当前 IDS 元数据中常规查询也均为同名表 `SELECT *` 形式。继续静态分析后已确认普通增量、历史衣架、ODP 手动同步和 OPEN 类独立线程的实现路径；“复表”在该副本中复制的是 `T_TableInfo` 映射配置行。以上不证明现场具体启用状态、目标对象或失败重试行为。回传端实际视图为 `V_ODP_Info`、`V_Hanger_Routing_Details`、`V_QC_Rework_Info`；7R 文档里的 `V_ProductData`、`V_ReworkData`、`V_ScrapData` 在对象目录中未找到。
4. 三个实际视图的业务粒度不同：`V_ODP_Info` 是报工明细记录；`V_Hanger_Routing_Details` 是衣架经过工位的路线事件记录；`V_QC_Rework_Info` 是缺陷/质检/返修相关记录。它们不是可以互换的日汇总表，也不能单靠其中某一个视图还原全部业务。
5. 当前实际视图没有能够明确表示“成衣尾查合格”的通用字段。`V_QC_Rework_Info` 记录的是质检问题和返修相关事实；没有查到返修记录不能证明该件衣服已通过尾查。现场标签打印必须使用产线数据库中经验证的明确合格事件。
6. 线计划号与 PO 号属于两个系统中的业务标识。现场试验已证明衣拿计划选择页允许同一线计划 ID 下存在多行颜色尺码；这不自动证明 IDS 每种视图均以同一字段完整回传 PO，也不证明所有版本都把 PO 作为 `TSPO_ID`。ERP 应保存显式映射，并用产线实际回传记录验证。

### 3.1 ERP/MES 下发给衣拿

7R 工作簿列出以下主要对象：

| 对象 | 字典所描述的职责 | 本项目中的理解 |
|---|---|---|
| `ToIna_Employee`（TIE） | 员工号、姓名、RFID、生产线、车间、组别、部门等 | 员工与组织的外部映射；字段里的部门/组别是否为稳定编码，须和现场配置核对 |
| `ToIna_Style`（TIS） | 款号、款式描述/品名、计划数量、产线及导入标记 | 款式主数据及衣拿导入状态；款号长度上限在字典中为 25 |

| `Tag_Info`（TGI） | 标签码、款色码、线计划、包号、数量、衣架键和扩展字段 | 标签/包码对接对象；当前 IDS 没有同名对象，但存在内部 `P_Barcode_Info` 候选表。静态客户端副本有独立的 `Barcode_Info` 同步路径；是否等价、是否在实际运行机器启用待确认 |

### 4.3 三号线 IHS_OPEN 同名视图的组成与 IDS 差异

三号线 `IHS_OPEN.dbo.V_ODP_Info` 和 `IHS_OPEN.dbo.V_QC_Rework_Info` 的完整 SQL 组成、字段来源、JOIN 条件及结构风险已逐项记录在[《三号线吊挂数据库结构与 IDS 映射核对》第 10 节](三号线吊挂数据库结构与IDS映射核对.md)。关键差异如下：

- IHS_OPEN 的 `V_ODP_Info` 共 47 列，按 `ODP_Detail` 明细键输出报工行；员工从 ODP 主单取，计划文本来自 `Style_Planned_Orders.STPO_ID`。视图没有 `WHERE`，而 IDS 中继的 42 列 `V_ODP_Info` 有 `DelFlag=0` 过滤，字段也不完全相同，不能当作逐列等价接口。
- IHS_OPEN 的 `V_QC_Rework_Info` 共 47 列，按 `QC_Rework` 质量事件输出；视图暴露的是计划内部 Key，不是计划号文本，也没有把底表的吊架 ID/Key 投影出来。IDS 中继 QCRI 则输出 `QCRI_STPO_ID` 文本字段，但同样没有单件衣架键。
- 两个 IHS_OPEN 视图按款式和工序编码关联款式路线，没有按路线节点 Key/工序顺序唯一匹配；当前结构不能排除同一款式重复使用同一工序编码时的多行匹配。此为 SQL 与唯一约束检查发现的风险，未读取实际路线行验证。
- ODPI 报工明细、VHRD 吊架工位事件和 QCRI 质量事件粒度不同，且没有共同的通用单件键；应分别建模和对账，不能仅凭 PO、款色码、员工、近似时间把它们拼成单件生产履历。

在本次检查的 IDS 对象目录中没有找到 7R 字典列出的 `V_ProductData`、`V_ReworkData`、`V_ScrapData`。用户确认该环境通过独立客户端工具配置吊挂数据上传，所以当前首先应核实这些对象是否未配置上传、客户端是否支持视图或查询结果同步，以及目标对象由谁创建；不能把缺项直接解释成软件不支持。若对象存在但没有同步记录，也按“客户端尚未配置该数据上传”处理。生产规划第 15.14.2/15.14.5 节因此仍须按实际启用的上传对象核对，不能假定每个部署都有 VPD/VRD/VSD。

### 4.4 ERP 读取的 IDS 核心回传视图：SQL 来源和统计边界

用户明确说明 ERP 获取吊挂产量、返修记录和员工生产记录主要依赖 IDS 的三个视图。本节因此以**中继库当前实际视图 SQL**作为 ERP 对接分析的主契约；三号线 `IHS_OPEN` 的同名视图只是源库侧证据，不能替代 IDS 侧字段定义。三个视图的逐字段来源、表 JOIN、过滤、关键风险已补入[《IDS 中继库全量结构盘点与文档差异》第 4 节](IDS中继库全量结构盘点与文档差异.md)。

| ERP 业务用途 | IDS 视图 | 主事实表与记录粒度 | 员工字段来源 | 关键统计/关联限制 |
|---|---|---|---|---|
| 工序报工与员工生产量 | `V_ODP_Info` | `P_ODP_Detail`，每条 ODP 明细一行；只筛 `ODPD.DelFlag=0` | 由 `P_ODP_Master.ODP_EM_Key + GroupId` 回连当前员工字典；员工是报工主单员工 | `ODPI_Quantity` 是报工明细数量；无聚合。工序路线按款式路线 + 工序编码补充顺序，未用节点键。`ODPI_Piece_Rate` 取 `B_Operation_Codes.OC_Piece_Rate` 当前字典值，不是明细历史工价。 |
| 吊挂工序/衣架流转与操作人员 | `V_Hanger_Routing_Details` | `P_Hanger_Routing_Details`，每条路线操作事件一行，再 INNER JOIN 衣架主档 | 来自路线事件 `HRD_EM_Key + GroupId` | 连接衣架主档用 `HRD_HM_ID = HM_ID + GroupId`，未用明细已有的 `HRD_HM_Key`，也未过滤主档 `DelFlag`；历史重复 HM_ID 可放大事件。每架件数会随着每个路线事件重复，不得直接对视图求和。 |
| 质量缺陷、送返修、修复记录 | `V_QC_Rework_Info` | `P_QC_Rework`，每条质量事件一行 | 缺陷人来自 `QCR_Defect_EM_Key`；名为 QC 员工的字段来自 `QCR_Sent_To_Rework_By_EM_Key`；修复人来自 `QCR_Repair_EM_Key` | 不含通过记录。底表有衣架 ID/Key 但视图没输出；`QCRI_LineNumber` 来自款式主档 `ST_Line`，不是质量事件的底表 `LineId`；视图 `GroupId` 来自质量原因字典而非事实表。 |

两个需要用于 ERP 建模的额外结论：

- 三个视图都是事实明细，不是日报汇总，也不共享可靠的单件关联键；报工数量、衣架每架件数、缺陷数和修复数口径应分开建模。VHRD 的衣架路线行数也不能当成衣服件数。
- 事实表外连当前员工、工序、工资类别和款式字典的描述字段会随字典维护而变化；若 ERP 要保留历史责任人、历史工价或事件时工序名，应以事实字段/同步快照为准并定义本地留存规则，不能假定视图提供的是不可变历史快照。
- ODPI 与 QCRI 都通过“款式 + 工序编码”匹配款式工艺路线，没有按具体路线节点 Key 连接；数据库没有相应组合唯一约束。对当前 IDS 有效路线按 `GroupId + STOP_STOPM_Key + STOP_OC_Key` 聚合核对，重复组为 0，暂未观察到当前有效路线造成的 JOIN 扩行；以后维护路线时仍应防止同款重复配置同一工序编码。
- QCRI 视图没有提供“检验通过/放行”事件。ERP 不可用“没有 QCRI 缺陷/返修记录”推定成品检验通过；一期标签打印仍要先在吊挂端找到并验证明确的尾查合格事件来源。

## 5. 关键字段的业务理解

### 5.1 线计划、订单与 PO

- `TSPO_ID` 是衣拿下发对象中的计划/订单号字段。7R 字典明确将其描述为“线计划号，或者订单号”；字段名本身不限定它就是客户 PO。
- IDS 的 `V_ODP_Info.ODPI_STPO_ID` 与 VHRD 的 `VHRD_STPO_ID` 由计划主数据关联得到，是衣拿计划对象的 ID 值。将其解释为客户 PO，必须有 ERP 下发映射或现场验证支撑。
- 用户已通过测试款确认：一个衣拿线计划号可以显示多种颜色和尺码的计划行。因此映射关系宜按“衣拿线计划 ID → ERP PO/内部生产任务”，而颜色尺码数量作为该计划下的明细；不能把一个颜色尺码行误认为一个独立 PO。
- 同一 PO 若拆给多条产线/多个车间，外部计划号是否仍可直接使用 PO 号取决于衣拿实例内唯一性范围；必要时外部线计划号应另行编码，再映射回同一 ERP PO。

### 5.2 ODPI 时间、数量和工资字段

`V_ODP_Info` 将几个不同的时间概念同时暴露出来：

| 字段 | 实际来源/含义理解 | 注意事项 |
|---|---|---|
| `ODPI_Date` | 报工主单日期 | 日期归属不等于每条工序的完成时刻 |
| `ODPI_Start_Time` | 明细 `ODPD_Start_Time` | 工序明细开始时间 |
| `ODPI_ODP_Actual_Clock_In` / `...Clock_Out` | 报工主单实际打卡/登录时间 | 主单员工计时区间，不能直接当成每一道工序的起止时间 |
| `ODPI_Actual_Time` | 视图映射的明细实际用时 | SQL 字段名不带单位；IDS Excel 也未给出明确单位，需供应商确认，不可照搬 VPD 的“秒”单位 |
| `ODPI_Quantity` | 明细报工数量 | 单位/是否衣服件数，应结合衣拿当前报工操作验证 |

工资字段需要特别谨慎：视图中 `ODPI_Piece_Rate` 映射到当前工序基础资料的计件单价，`ODPI_PA_CurrencyValue` 映射到薪资类别的金额；而底层 `P_ODP_Detail` 还保存 `ODPD_Pay_Rate`、`ODPD_Piece_Rate` 等明细字段，当前视图没有把这些明细金额字段暴露出来。因此不能直接把视图中的当前工序单价解释成“此报工发生当时的历史工资单价”，也不能用它单独复算历史工资。

### 5.3 VHRD 的衣架、包牌与工序事件

- `VHRD_HRD_Key` 是路线明细事件键，可作为该条事件的外部去重键候选；仍须确认中继同步是否会更新/删除既有事件。
- `VHRD_HM_ID`、`VHRD_HM_Key` 标识衣架；衣架会回收复用，所以这两个值应解释为载具身份，不是永久成衣身份。
- 底层 `P_Hanger_Routing_Details` 还存在 nullable 的 `HRD_HM_Key`，但当前 VHRD 定义没有使用它，而是按 `HRD_HM_ID = HM_ID + GroupId` 连接；VHRD 也没有过滤 `P_Hanger_Master.DelFlag`。只读聚合检查发现衣架主表有 11,562 个重复的 `HM_ID + GroupId` 组合，其中 11,235 组包含 `DelFlag=1` 行；`DelFlag` 的 0/1 含义没有数据库注释，不能直接断定 `1` 就是历史/删除状态。由于本轮没有对约 298 万行的路线明细做全量连接计数，视图实际被放大的事件数量尚未量化；但按现有连接条件，重复连接及带出非当前衣架主档信息的风险明确存在。要用于单件追踪或数量对账前，需向厂商核实 `DelFlag` 口径、`HRD_HM_Key` 有效率及正确关联方式。
- `VHRD_HM_Item_Card` 字典称为扎牌号码；字段名暗示是衣架主档上的卡片/标签标识，但它是否等于 ERP 包码、是否能唯一对应一件成衣或一组裁片，须现场扫读数据和挂片动作确认。
- `VHRD_HM_Garments_Per_Hanger` 是衣架对应的服装/裁件数量口径。字段名不能证明“一衣架恒等于一件成衣”；需验证拆挂、合挂、返修和一架多件场景。
- `VHRD_HRD_ODP_Credited` 是是否计入产量/工资统计的标志。它不是质量通过标志，也不能单独证明衣架已经下线。
- `VHRD_HRD_Started_Time`、`VHRD_HRD_Completed_Time` 是事件级起止时间；它们与 ODPI 的主单打卡时间不是同一概念。
- `VHRD_STPO_ID` 是衣架主记录关联计划后得到的计划号；这是目前 IDS 视图里核对 PO/线计划归属的重要字段候选，但仍要用挂片时选择的线计划做实际回传测试。
- 当前 VHRD 包含衣架当前位置、当前线、加载线、路线图键和返修标记等信息。这些状态描述的是衣架/生产流转上下文，不应未经验证直接作为“成衣已包装/已入库/尾查合格”的状态。

### 5.4 QCRI 的质检与返修

- 可确认的字段覆盖缺陷产生人/时间/数量、款式/工序/颜色尺码、质量原因、是否需要返修、质检站位/时间、修复人员/时间/数量以及 PO/计划号。
- 视图底层 `P_QC_Rework` 有 `QCR_HM_ID` 和 `QCR_HM_Key`，但当前发布的 `V_QC_Rework_Info` 没有把这两个衣架关联键暴露出来。仅用 QCRI 无法可靠地把返修行与某一件吊挂衣服匹配。
- 字段 `QCRI_QC_EM_Key` 在实际视图定义中来自 `QCR_Sent_To_Rework_By_EM_Key`。字段文档把它标作“质检员工工号”，但来源名表示“送返修人”；在厂商解释前，不能认定它一定是实际执行检验的员工。
- `QCRI_QCSC_Is_Rework` 区分质量原因是否需要返修，不等同于质检合格/不合格的完整状态流。
- 视图没有通用的“检验通过”状态列。因此一期打印程序不能用“没有 QCRI 返修记录”作为尾查通过判据。
- `QCRI_LineNumber` 的实际 SELECT 表达式是 `B_Style_Master.ST_Line`，而 `P_QC_Rework` 自身有独立的 `LineId`；当前视图输出的是款式主档的线号，不能拿它还原质量事件实际发生线。`GroupId` 也由 `B_QC_Sub_Codes` 提供：原因字典匹配缺失时，该输出列可能为空，ERP 应使用已核实的事实组织键或在本地落库时保留同步来源上下文。

### 5.5 7R 标签接口与 IDS 内部条码表

- 7R `Tag_Info` 字典提供 17 个字段；当前 IDS 没有同名表，但存在内部 `P_Barcode_Info`，有 16 个字段。静态客户端副本中能看到源 `Barcode_Info` 的变更跟踪查询、以 `BCI_Key` 关联以及写入/更新 `P_Barcode_Info` 的 SQL 模板；删除变更会被转换成 `DelFlag` 标志。这说明该副本实现了条码信息的线体至 IDS 数据通路，但不能证明实际运行机已启用。
- 两套字段有明显的命名/类型相近项，例如 `TGI_TagID` 与 `BCI_LabelID`、`TGI_StyleID` 与 `BCI_StyleID`；但它们不是可以直接一对一照抄的接口。7R 将颜色 ID 与描述拆成 `TGI_ColourShotDes`、`TGI_ColourDes`，而 `P_Barcode_Info` 只有 `BCI_Colour`；`TGI_PlannedOrders`、`TGI_PerQuantity`、`TGI_MaxMantissa` 在内部表中没有对应列。其余候选字段对应见全量盘点文档的字段表。
- 本机副本配置里的 `Barcode_Info` 开关为 `false`。运行客户端主页面截图显示部分线体源在同步，但没有条码项或映射设置，不能据此说明实际生产机器的 `Barcode_Info` 开关状态。还需从运行机器的参数/数据表配置界面核验，并向衣拿确认 `P_Barcode_Info` 是否就是 7R `Tag_Info` 的 IDS 内部承接表。

## 7. 对接落地的统一理解

### 7.1 ERP 内部对象与衣拿外部标识分开

ERP 应维护自己的稳定业务主键和业务规则。衣拿的款号、线计划 ID、员工号、工序码、线号、站位号和衣架号作为外部标识保存，并按“厂商/产品/软件版本/系统实例/产线”范围建立映射。除非经过配置与验证，不根据两个字符串碰巧相同就认定它们是同一业务对象。

建议至少保留以下映射关系：

| ERP 业务对象 | 衣拿字段候选 | 映射边界 |
|---|---|---|
| 款式/产品 | `TIS_StyleID`、视图 `...ST_ID` | 受衣拿款号长度、同一数据库内唯一性约束 |
| 员工 | `TIE_ID`、视图中的 `...EM_Key` | ERP 员工 ID 与衣拿员工键/工号分开存；`SSN` 等敏感字段按最小必要原则处理 |
| 工序 | `TISO_Op_Code`、`...OC_Key`、工序顺序字段 | 工序编码、数据库内部 Key 和显示名称分别保存 |
| 车间/产线/站位 | `TIE_Line`、`TSPO_Line`、`TIRM_Line`、`...Workstation` | 建立系统实例和产线范围内的映射，避免跨车间同号冲突 |
| 客户 PO/生产计划 | ERP PO/任务 ID ↔ `TSPO_ID`/`...STPO_ID` | 允许一个 PO 对一个外部线计划，也允许因产线拆分而一 PO 多外部计划；按数量明细对账 |
| 吊挂工位事件 | `VHRD_HRD_Key` | 作为源系统事件 ID 候选；需补充变更、撤销和迟到记录策略 |
| 质检/返修记录 | `QCRI_Key` | 是质量事件键，不一定具有单件唯一关联能力 |

### 7.2 分开处理三个使用场景

1. **ERP 下发吊挂计划**：将一个 PO/生产任务映射为目标吊挂实例内的线计划 ID；同一线计划可以有多条颜色尺码计划行。下发的工序、颜色、尺码、员工和路线均需按当前目标实例的表结构映射。
2. **ERP 从 IDS 同步生产记录**：按实际 IDS 的 ODPI/VHRD/QCRI 读取和转换为 ERP 统一事件，不把厂商视图名称直接等同 ERP 本地表语义。ODPI 产量、VHRD 工位路线、QCRI 缺陷返修分开建模并分别对账。
3. **吊挂线现场尾查后打印**：打印工具读取一号车间真实吊挂产线数据库；IDS 是 ERP 中继同步的数据源，不是一期现场打印触发器。打印规则需从产线数据库找到明确的合格结果、稳定事件键、PO/线计划、颜色尺码、生产小组、尾查人员和下线时间。

### 7.3 增量同步与性能

检查时 `P_Hanger_Routing_Details` 约有 298 万条记录（数据库统计估算），在已检查索引元数据中只看到其主键 `HRD_Key` 索引，没有看到开始/完成时间字段的索引。`V_Hanger_Routing_Details` 是未聚合的明细视图。

因此，规划中“每 1–5 分钟轮询整个 VHRD 视图”不能直接当成可上线的读取方式。开发前应确认衣拿支持的增量同步机制、更新时间/递增序号及相关索引；如果只能按时间回查，还要验证迟到事件、历史更新和重复数据的覆盖范围。不得假定 GUID 主键按时间递增，也不得依赖全表反复扫描来满足实时性。

## 8. 仍需现场/厂商确认的问题

### P0：会影响 PO 标签和事件正确性

### P1：会影响工资、工序追溯和质量归责

- `ODPI_Piece_Rate`、`ODPI_PA_CurrencyValue` 是当前配置值还是报工时快照？真实历史计薪使用底层哪些字段，调价后旧记录会不会更新？
- `QCRI_QC_EM_Key` 映射到“送返修人”是否为设计预期？谁是实际检验人，字段是否区分？
- QCRI 的缺陷数量、返修数量、修复数量是按衣服件数还是质检缺陷数？同一件有多个缺陷、返修多次、复检时如何形成多条记录？
- 是否有单独的通过/放行记录视图或表？能否扩展 QCRI/VHRD 使质量事件带衣架/单件标识？

### P2：会影响多车间可复制性和同步运维

- 7R `Tag_Info` 的安装位置和授权要求是什么？当前 IDS 没有同名对象时，是否由衣拿产线库读取，还是使用 `P_Barcode_Info` 等内部结构？

- 当前 IDS 的颜色、尺码资料是谁维护，ERP 下发是否需要先写 `ToIna_Colour`/`ToIna_Size`？颜色/尺码 ID 在不同系统实例内是否可重复？
- 当前生产数据同步软件的版本、授权、延迟、删除/修订传播规则及推荐增量游标是什么？
- 表信息页保存的 `SelectSql` 是否会被现场运行版本的任一同步线程读取？已检查的本机副本中，自动上传方法按源表名选择内置 SQL 模板，未发现同步业务方法读取 `SelectSql` 属性。
- 一号车间数据库、IDS 中继和其他车间未来版本如何分别提供只读账号、备份和恢复？
- 视图字段变更如何通知 ERP？是否能由供应商提供每个版本的正式 DDL/视图定义及升级说明？

## 9. 与现有规划的差异及维护建议

当前 [`生产流程规划.md`](../../规划/系统与流程/生产流程规划.md) 第 15.14 节同时写了 VPD/VRD/VSD 聚合回传和 IDS 的 ODPI/QCRI 明细回传，并把 VHRD 用于衣架级单件绑定。此次现场目录核对显示，当前被检查的 IDS 实例只有 ODPI、VHRD、QCRI 三个回传视图，且 QCRI 未暴露衣架关联键、VHRD 使用可复用衣架键。两者不宜合并表述为一个已经统一验证的接口契约。

当前规划中“VHRD 衣架级明细可完成件码↔衣架绑定”和“QCRI 为件级质检返修明细”的**业务目标可以保留，但现有视图结构还不足以证明这两个实现结论成立**：IDS QCRI 没有底表中的衣架 ID/Key；三号线 IHS_OPEN QCRI 也只输出计划内部 Key，不输出衣架 ID/Key；VHRD 通过可复用衣架标识关联，且一个衣架可能代表多件挂衣。只有验证吊牌卡号字段在挂片/移架/返修/回收再用时的写入与保留规则、QCRI 的件数粒度、以及客户端映射到 IDS 后的键保真，才能确认具体的单件绑定模型。当前应把 `hanger_item_binding` 和 QCRI 驱动的单件返修闭环看成待验证接口设计，不当作现有数据已具备的能力。

同时，规划列出的 VPD/VRD/VSD 聚合视图未出现在当前 IDS 对象目录中；用户确认对象缺失或无上传记录表示同步客户端未配置该对象。当前不能假设这些聚合视图正在供 ERP 使用。ERP 的实际数据消费合同、同步客户端的 ODP 转换方式、以及这些聚合视图是否会在目标部署中启用，应分别核实后再把 15.14 节的同步和工资/返修口径标成可落地。

本文件先作为数据库技术参考记录现场证据和未决项，不自动把旧规划段落覆盖成“已经核实”。后续形成经供应商确认的接口合同后，再同步更新规划中的对象清单、事件粒度、PO 映射、数据同步策略和件级追溯结论。字段语义、类型或映射发生变化时，保留旧版本核对记录，并标注对应吊挂软件版本与系统实例。
