## 一、目标与边界

组织架构维护企业内组织节点及上下级关系，为人员归属、组织查询和数据权限提供统一组织树。组织架构表达“组织节点及汇报/归属层级”；业务管辖关系是独立关联，不通过改变组织树表达。

- 组织架构归“人员”模块；岗位管理、角色管理仍是独立功能（角色管理归系统模块）。
- 建筑档案是物理空间，归物业资产；组织节点可关联所在建筑，不能把建筑本身等同于组织节点。
- 小组属于组织节点的一种业务类别，使用组织架构维护；人员档案保存人员主归属和小组关联。
- 组织树是统一数据范围的物理载体；具体权限仍由角色权限与数据范围规则控制，组织架构不自行实现一套权限系统。

## 二、组织模型

### 2.1 节点关系

- 组织节点通过父节点构成树；节点包含自身及祖先路径，层级展示由树关系计算，不将树深度写死在页面逻辑中。
- 可从顶层节点开始逐级建立组织；新增、修改父节点或停用前需检查人员、子节点和业务引用，具体校验规则以实现契约为准。
- 人员只设置一个主归属组织节点；岗位/角色与组织归属分开维护。
- 小组节点可作为其他小组的上级，支持如“缝纫组 → 缝纫1组”的嵌套；负责人关联系统人员。

### 2.2 建筑与组织节点

- 建筑档案与组织节点分离；车间类节点可关联建筑，后续组织节点可沿祖先关系取得建筑信息。
- 节点的位置可记录建筑、楼层和补充位置，列表可组合展示；建筑选择与楼层选项联动。
- 仓库是库存业务地点，不因其位于建筑内就自动成为组织树节点。

### 2.3 组织树与业务管辖

- `sys_org_manage` 用于表达管理方节点与被管节点之间的多对多业务管辖关系。
- 业务管辖关系不改变组织树父子层级；管理方可在组织架构中选择被管节点。
- 删除/停用前需检查该节点是否仍被其他节点管辖；禁止留下悬空关联。

## 三、页面与操作

### 3.1 页面布局

- 页面采用左侧组织树、右侧组织列表的主从布局。
- 点击树节点后，右侧显示该节点及其下级范围；提供“显示全部”恢复全量列表；树可收起。
- 树节点展示名称及节点类别；小组可与普通组织节点区分显示。
- 列表和表单遵守《前端规范.md》的统一列表、筛选、表格与弹窗规范。

### 3.2 当前已记录的操作/字段

| 项目 | 当前规则或已记录设计 | 来源/说明 |
|---|---|---|
| 组织名称 | 组织节点名称；支持按名称查询 | 组织管理实现记录 |
| 上级组织 | 通过树选择父节点；允许创建顶层节点 | 功能命名清单、开发日志 |
| 层级 | 由祖先关系计算，展示“N级”；筛选按层级 | 后续实现记录；与早期固定四层分类表述冲突，见第六节 |
| 状态 | 列表可按状态筛选；停用对人员与业务引用的影响需补充契约 | 人员管理增补记录 |
| 所在建筑 | 组织节点可关联建筑档案；当前记录为车间层关联，子节点按祖先关系取得 | 物业资产/组织架构增补记录；适用层级待统一 |
| 楼层/位置 | 楼层可按建筑联动选择；补充位置与楼层组合展示 | 人员管理增补记录 |
| 业务管辖 | 管理方组织选择被管组织；支持多选；展示管辖数量 | `sys_org_manage` 设计记录 |
| 小组类别 | 小组节点通过类别标记；可嵌套；负责人关联用户 | 小组管理增补记录 |

## 四、与其他功能的关联

- **人员信息**：人员主归属组织保存在人员记录；小组关联以小组节点 ID 为准，显示名称可冗余但不能代替 ID。
- **权限与组织树**：查询数据范围按“用户主组织节点 + 角色数据范围”计算；遵循《地基/权限与组织树.md》。
- **岗位管理**：岗位是员工岗位/职责，不是组织节点；岗位不因组织树节点新增而自动新增。
- **建筑档案**：组织节点引用建筑档案 ID；建筑信息维护见《模块-物业资产.md》。
- **生产模块**：车间/区域/小组等节点为生产归属和人员分组提供组织基础，业务数据按具体单据契约引用。

## 五、命名与数据约束

- 功能名称：组织架构。
- 现有功能英文标识：`org`，现有主表口径：`sys_org`；展示名称调整不代表重命名表或 API。
- 小组仍是组织树中的节点，不因页面是否提供单独卡片而拆出另一套组织数据。
- 组织节点 ID、人员 ID、建筑 ID 等大整数在前端/API 按字符串传输，禁止转为 JS Number；遵守《开发规范.md》大整数规则。
- 用户可见文案使用“组织架构/组织节点”等当前术语；历史开发日志中的“部门管理”只保留为历史记录，不作为当前入口名称。

## 六、待统一/确认事项

以下内容在现有文档记录中存在不同表述，未确认前不扩展数据库或权限规则：

1. **层级类型口径**：早期已定稿内容写“厂 → 车间 → 区域 → 小组”，后续实现记录改为树深度动态计算，并出现 `org_category='N级'`；小组记录又使用 `org_category='小组'`。需明确类别字段是业务节点类型、层级显示值，还是二者分开。
2. **建筑关联层级**：有记录称车间层关联建筑、子节点继承；也有旧表述称各组织节点均可维护所在建筑/楼层/位置。需确定哪些节点可直接关联建筑、哪些字段继承。
3. **小组所属车间**：已有文档按祖先链取所在建筑推导，但建筑可容纳多个车间；应确认所属车间应取最近的车间类型祖先，而不能仅凭建筑 ID 推导。
4. **删除、停用和移动**：分别明确有人员、子节点、业务数据或业务管辖引用时的允许条件、迁移处理和审计留痕。
5. **负责人规则**：小组是否必须有负责人、负责人离职/调组后的处理方式。
6. **功能命名术语**：现用标识 `org` 保持不变；“组织架构”的英文术语按《术语词库索引.md》由负责人补充登记，不改变现有表/API 标识。
