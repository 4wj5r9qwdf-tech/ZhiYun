## 零、技术栈（定稿 2026-10-23）

> 判据：稳定性 / 可靠性 / 可用性 / 安全性 / Codex 可维护性（团队啥语言都不熟，全靠 Codex 写，故取"确定性高、类型安全、生态成熟"）。判据已含"能不能用权限/开关/自填就不写死"，与后文各规范一致。

### 服务端（一语言到底：Java）
| 层 | 选型 | 说明 |
|---|---|---|
| 语言/框架 | **Java / Spring Boot（裸 Boot + 按需 starter，打底 RuoYi-Vue-Plus）** | 取 RuoYi 的"用户/角色/权限/审批/站内信通知"现成底座，裁掉用不到的（代码生成/多租户/监控全家桶） |
| 主库 | **PostgreSQL** | ERP 核心 |
| 向量库 | **pgvector**（建在 PG 里） | 知识库 RAG 检索，零额外组件/零额外故障点 |
| 吊挂/中继 | **SQL Server**（7R/IDS，衣拿） | 只读拉取，跨库收在**适配器**（幂等 + 断线补传，见 15.14），业务层只读 ERP 本地表 |
| 审批 | **Warm-Flow（原生集成，仿钉钉节点自定义）** | 节点增删/调序/会签或签/条件分支/转交/加签/代理；审批结果回调业务模块 |
| 定时任务 | **XXL-Job** | 审批催办 + 业务预警 + 吊挂拉取；高可用调度（替换旧项目 threading.Timer） |
| 大模型 | **OpenAI 兼容 API**（LLM/TTS/ASR + embedding 走 `.env` 的 `EMB_*` 等） | 语言无关，HTTP 调；密钥只进 `.env`（红线见 十） |

### 中间件 / 存储（补齐，不堆运维负担）
| 组件 | 选型 | 为什么加（真实业务理由，不是"别人都有"） | 一期形态 / 升级口子 |
|---|---|---|---|
| 缓存/消息 | **Redis** | ① 订单要**上传合同/图片**等文件，上传前校验、临时态、断点/去重；② 各基础资料**导入导出**的高频临时数据、去重键；③ 站内信 SSE 多端实时推送的集中缓存+发布订阅；④ 吊挂幂等键、XXL-Job 分布式锁 | 一期就加（**现加比后期重调省事**——你定的）；Docker 单机；凭据进 `.env` |
| 对象存储 | **MinIO**（S3 兼容，Docker 单机） | 订单合同/图片、导出 Excel、公司 logo、附件（临工协议/社保材料）、知识库文档原件——**所有"文件/二进制"落这里** | 走 **S3 接口抽象层**，可替换 OSS/COS/本地盘；DB 只存 key+元信息，不存本体；凭据进 `.env` |

**"是文件就 MinIO，是数据就 PG，是代码就 Git" 三摊分清**：业务数据进 PG、`sql/主建表.sql`/代码进 Git、大文件/二进制进 MinIO。Redis 管"高频临时态/缓存/去重/实时推送"，MinIO 管"文件本体"，两者不重叠。

### 部署
- **OS = Ubuntu**（Java/PG/SQLServer适配/XXL-Job/Redis/MinIO 全支持；Warm-Flow 原生集成无需独立 OS 选型）
- 数据库双库：PG（主）+ SQL Server（吊挂/中继），跨库全收在适配器
- **Redis + MinIO 走 Docker 单机**（够几百人单体的量，不上一上来分布式多节点；要加节点/加盘时 MinIO 自身支持、代码零改）
- **文件上传/导出的统一规则**：订单合同/图片、基础资料导入导出、附件，**上传前先走 Redis 做去重/临时态，本体落 MinIO，PG 只存 key+元信息**；这条跟"内嵌智能体读文件/知识库摄入文档原件"共用同一对象存储

### 并发与容量（千人规模，定稿 2026-10-24）

**判定（依据用户确认的三点）**：三车间全开 ~1000 账号，但**报工分散（小程序各扫各的、线下实时）、同一秒集中操作基本没有、是每天每条线每人都用的长尾持续使用** → **属中并发、长尾持续，不是洪峰高并发**。现在这套 单体 + PG + Redis + MinIO 撑得住，**不预先把应用做分布式**（徒增运维、用不上）。

**两条软要求（卡开发写法，不是加组件）：**
1. **写路径轻快（报工/吊挂）**：报工 = 单条轻量 INSERT，不在写路径现算产量/工资（聚合推到读侧/定时侧）；不写长事务。吊挂走 XXL-Job 批量拉 + Redis 幂等去重，不实时逐条打 PG。Redis 承担报工去重 + 零散写抖动吸收 + 临时暂存。一句话：写路径快进快出，重活推给读侧和定时侧。
2. **读路径走缓存 + 预聚合（看板/产量/工资）**：产量/考勤/在制走预聚合（XXL-Job 按小时/天聚好存表，看板读聚合表，不现跑全表 group by）；热点聚合结果 Redis 缓存；工资月度批算不实时。

**扩容触发条件（不现在做，留无状态口子）**：任一满足才启动应用加实例 + 负载均衡（架构不用改——应用无状态，会话/缓存/锁全在 Redis）：

| 触发指标 | 阈值 |
|---|---|
| 持续 QPS | > 500 |
| PG 慢查询(>1s)占比 | > 5% |
| 报工接口 P99 延迟 | > 1s |

> 一期预估峰值 QPS 一两百，离 500 红线有 2-3 倍余量，单机 + Redis 够。数字（500/5%/1s）走配置表/.env（CAP_QPS_LIMIT / CAP_SLOW_SQL_RATIO / CAP_P99_MS），换阈值改配置不改代码。

**一期压测验收目标**：模拟分散报工 + 看板查询，P99 < 300ms、QPS 500 不崩，不达标不放过。

### 安全性（新增硬约束，全栈通用）
1. **认证/授权**：Spring Security + JWT/会话；**数据权限按"组织树 + 角色"过滤**（同 地基/权限与组织树），敏感数据（身份证/手机号/工资/密码）**脱敏展示**、按权限可见。
2. **密钥/凭据**：DB 密码、模型 key、供应商凭据**一律进 `.env`，不进代码/Git**（见 十、配置红线）；`.env` 进 `.gitignore`，仓库只提交 `.env.example`。
3. **传输**：内外网部署用 **HTTPS**；跨内网（192.168.x）组件间走内网 + 最小化开放端口。
4. **注入/越权**：SQL 用参数化（ORM/MyBatis 参数绑定，禁拼 SQL）；**智能体每次操作以发起员工身份校验（权限红线，见 十）**，无权限动作不可见/不可执行。
5. **日志留痕**：敏感操作（改权限、删数据、切品牌、审批）全程留痕（谁/何时/改了什么），软删不物理删（同 15.15.10 那套）。
   - 新增功能的日志与功能同步设计、开发和验收。新增、修改、删除、启停、审批、权限调整、导入等业务操作应记录操作者、时间、中文业务动作、对象 ID 与可识别名称或编码、结果。数据变更记录实际变更字段及前后值，批量操作记录对象范围和结果。敏感字段按业务规则脱敏，凭据不入日志。
   - 验收时从系统日志入口查看实际记录，确认能识别操作与对象、追溯变更。请求路径、HTTP 方法和通用日志注解不能替代业务审计明细。
6. **供应链**：RuoYi-Warm-Flow/依赖 固定版本 + 锁定，定期扫已知漏洞（CVE）；不引入不必要重型组件（够用就好，同 八 成本取向）。

> 联动更新：知识库向量库 原"Chroma 嵌入式" → 改为 **pgvector（建在 PG）**；审批原"Warm-Flow 独立小服务" → 改为 **Warm-Flow 原生集成（RuoYi-Vue-Plus 打底）**；数据库主库 由 SQL Server → **PostgreSQL**（吊挂仍 SQL Server）。凡文档/规范里旧的"Chroma/小服务/主库SQLServer"表述，以本条为准。

## 一、文档命名规范（技术栈无关，立即执行）

1. **所有文档文件名必须使用中文**（`README.md`、`CHANGELOG.md`、`LICENSE` 等行业惯例文件除外），扩展名保持不变（`.md` / `.xlsx` / `.docx` 等）。
   - 例：`生产流程规划.md`、`开发规范.md`、`数据库字典.md`，不用 `ProductionFlow.md`、`DevSpec.md`。
2. 文档内部章节标题使用中文，编号用"一、二、三"或"1、2、3"，不使用英文章节名。
3. 文档统一放在 `Docs/` 目录下，禁止散落在代码目录。
4. 每份文档头部必须有"版本 / 更新日期 / 说明"三行，更新日期字段每次修改文档时必须同步更新。
5. 需求讨论过程中产生的"上下文交接总结"（如旧项目的长会话记录）在整理进正式文档后，原始会话记录文件需改名加前缀存档（如 `_会话记录-xxx.md`），不与正式规范文档混排。

### 1.1 路径与地址规范（强制）
1. **文档内部、代码注释内部，引用文件/目录一律使用项目内相对路径**，禁止出现本地电脑盘符（如 `D:\ZhiYun\...`、`C:\Users\...`）。
   - 错误示范：`参见 D:\ZhiYun\Docs\生产流程规划.md`
   - 正确示范：`参见 Docs/生产流程规划.md`（以项目根目录为基准的相对路径）
2. 代码里引用项目内文件（配置文件路径、模板路径、资源文件）必须用项目内相对路径或环境变量占位，不允许把开发者本机绝对路径硬编码进代码提交。
3. **Git 提交（代码、文档、注释、diff）中不允许出现本地绝对路径**：提交前自查，发现 `C:\`、`D:\`、`/home/xxx/` 等本地路径一律替换为项目内相对路径后再提交。

### 1.2 目录结构规范（强制，2026-10-24 新增）

1. **绝对不允许出现嵌套 Git 仓库**：项目根目录下只能有一个 `.git`。禁止 `git clone` 或 `git init` 产生子仓库（踩过的坑：RuoYi-Vue-Plus 克隆时自带 `.git`，被 Git 当 submodule，必须删掉子 `.git` 再加入）。
   - 引入第三方开源代码时：克隆后**先删子目录的 `.git`**，再 `git add`；或走 `git submodule`（本项目不采用，保持单仓库）。
   - 自查命令：`find . -name '.git' -type d | grep -v '^\./\.git$'` —— 结果必须为空。
2. **自建目录层级深度 ≤ 3 层**（以项目根为第 0 层）：鼓励扁平结构，不写"套娃式"深层目录。
   - 当前达标：`Docs/`（0→1→2 层，最深 `Docs/知识库/工艺SOP` = 2 层）。
   - **豁免**：第三方库目录（如 `RuoYi-Vue-Plus/`）内部的 Java 包路径（`src/main/java/org/dromara/...` 深至 12 层）属包命名规范，**不受本条限制**；自建代码若需包路径，按语言惯例（Java 包结构）豁免，但**业务目录/文档目录/配置目录一律 ≤ 3 层**。
   - 新增目录前自查：`find <新目录> -type d | awk -F/ '{print NF-1}' | sort -rn | head -1` 不得超过 3。
3. **不重复建同类目录**：一个用途只开一个目录（如文档统一 `Docs/`，不建 `doc/`、`document/`、`docs2/`）。

## 二、功能命名与登记规范（强制维护口径，不设逐项审批门槛）

1. **功能命名清单是统一登记和查重依据，不是开工审批表**。用户已给出名称时沿用；没有明确名称时，负责人结合业务范围、现有模块和术语词库选取最贴切名称，并登记到《功能命名清单》，不因普通命名选择停工等待确认。
2. 命名处理规则：
   - 优先沿用用户用语、现有产品入口名和词库既定术语；检查是否与现有功能重复或边界冲突。
   - 新名称按业务对象和实际功能范围确定，登记中文名称、词库英文口径、对应表及备注；在任务记录中说明必要的命名判断。
   - 只有名称选择会改变业务边界、与既有功能发生实质冲突，或影响已被外部系统依赖的公开接口/表名时，才说明影响并请求用户决策。
3. **数据库表名必须与该功能名称严格对应**：
   - 表名 = 功能名称（中文）对应的英文小写下划线翻译 + 业务域前缀，翻译口径由"功能命名清单"统一定义（同一功能全系统只用一个英文表名前缀，禁止各模块各译各的）
   - 示例：功能名"布卷档案" → 英文口径定为 `fabric_roll` → 对应表名 `base_fabric_roll`（基础域前缀 `base_`）
   - 禁止出现"功能名是A，表名却是B"的脱节：表名必须能在《功能命名清单》里反查到对应的中文功能名
4. 一个功能涉及多张表（主表+明细表+日志表）时，主表名=功能英文名，明细表=功能英文名+`_item`/`_detail`，日志表=功能英文名+`_log`，口径统一，避免各写各的。
5. 功能名称需要调整时，先核对业务边界和已有数据/API 依赖，再更新《功能命名清单》及相关文档；涉及已建表或外部接口时按兼容迁移规则处理。单纯改善显示文案不改变业务含义时，不要求用户逐项批准。


6. **需求变更/新功能先明确业务目标和关键边界，之后在授权范围内自主实施**：
   - 用户提出明确实施请求时，负责人简要复述业务目标、范围、关键输入输出和验收标准；简单任务无需单独计划，复杂任务建立功能任务单。
   - 用户明确要求“实施/开始做/按方案开发”即为开工授权。用户已确认的规划、任务单或本次对话中的业务规则作为依据；不要求把每个字段、表列、接口细节、校验方式和文件改动逐项提交用户批准。
   - 负责人自主选择符合现有架构和规范的实现方案，完成代码、DDL、测试、相关文档和开发环境迁移；在任务单记录重要实现选择、风险及实际结果。
   - 只有涉及业务目标/数据含义变化、关键业务规则缺失或冲突、扩大到无关模块、改变权限/审批规则、重要数据不可逆影响、生产迁移/部署，或引入明显外部成本时，才暂停并向用户说明具体影响、给出建议后请求决策。
   - 文档应与实现同批维护；无需为了补计划文档或等待普通命名/技术细节审批而阻塞已授权且规则明确的实现。新功能名称按本节规则自主确定并登记；名称已确定的功能直接复用。

7. **英文命名依据《术语词库索引.md》+ 服装加工厂专业名词词库.json**：功能英文名、表名、字段名出现英文时，先查词库既定口径，没有才新增并回填 JSON；禁止拼音缩写或机翻（详见《术语词库索引.md》第二节使用规则）。

## 三、数据库规范（技术栈无关，立即执行；具体实现细节随技术栈落地）

### 3.1 表与字段注释
1. **所有表必须带注释**，注释用中文，说明该表承载的业务含义，不是重复表名翻译。
2. **所有字段必须带注释**，注释用中文，写明该字段的业务含义。
   - 错误示范：`material_id` 注释写"物料id"（无信息量，等于没说）
   - 正确示范：`material_id` 注释写"关联 物料档案表.id，本行物料对应的物料档案主键"
3. 外键字段注释必须写明关联的表名和字段名。
4. 字典/枚举字段（如裁剪类型、供料标识）注释必须列出全部合法取值，例如"裁剪类型：面布/里布/衬布/配色布/配布/其他辅料"。
5. 金额字段注释必须写明单位（元/分）和精度（如 `DECIMAL(12,2)`）。
6. 布尔字段注释必须写明"1=是/0=否"或"true/false 分别代表什么业务状态"。

### 3.2 命名约定（先查词库，不自造）
**所有表名、字段名、数据取值（字典/枚举）的英文别称，一律先查《术语词库索引.md》+《服装加工厂专业名词词库.json》既定口径；没有才新增并回填 JSON，禁止拼音缩写或机翻。** 与 4.3 命名依据、功能命名规范第 7 条 一致。

| 对象 | 规则 | 示例 |
| 对象 | 规则 | 示例 |
|---|---|---|
| 表名 | 小写下划线，业务域前缀 + 名词 | `prod_cut_spread`（生产域-拉布记录） |
| 主键 | 字段名去掉域前缀 + `_id` | `piece_id` |
| 外键 | 关联表名 + `_id` | `material_id`、`order_id` |
| 布尔 | `is_` 开头 | `is_disabled` |
| 时间戳 | `_at` 结尾 | `created_at`、`confirmed_at` |
| 数量（件/个） | `_qty` 结尾 | `surplus_qty` |
| 米数（布料） | `_meters` 结尾 | `used_meters` |
| 金额 | `_amount` 或 `_price` 结尾，单位分/元须在注释写明 | `commission_price` |

### 3.3 迁移与一致性
1. 所有 DDL 变更（建表/加列/改索引）必须集中管理，禁止散落在业务代码里隐式建表。
2. 新增字段必须带默认值，禁止新增 `NOT NULL` 字段无默认值导致老数据插入失败。
3. 开发环境、测试环境、生产环境的表结构必须保持一致，任何一处加列后其余环境须同步（旧项目 `cost_variance` 表曾因漏同步 `variance_pct`/`status` 两列导致成本告警功能测试失败的教训，禁止重演）。
4. DDL 变更单独一次提交（见 Git 规范），不与业务逻辑改动混提交，方便按提交粒度回滚。

### 3.5 DDL 主 SQL 合并规则（强制，不零散）
1. **开发期可分模块建零散 DDL 文件**（`sql/<模块>.sql`），方便逐功能开发；但**每个功能经用户验证"没问题"后（见 十一、功能开发节奏铁律 第 3 步），其 DDL 必须合并进一个"主 SQL"文件** `sql/主建表.sql`（或 `sql/schema.sql`），不允许零散文件长期散落。
2. **主 SQL 是唯一权威建表入口**：新环境（测试/生产）初始化一律跑这一个主 SQL，不靠"挨个跑零散文件"；零散模块 DDL 在合并进主 SQL 后**可归档删除**（进 `sql/archive/` 或走 Git 历史），不留"既零散又有主 SQL 两份口径"。
3. **合并时机 = 功能验证通过后、发版本记录前**（同 十一、第 4/5 步同批次），与 DDL 单独提交（3.3 第 4 条）配合：先模块 DDL 单独提交开发 → 用户验证过 → 合入主 SQL 单独提交 → 版本记录记"已并入主 SQL"。
4. 主 SQL 内按"模块/地基"分区块注释（`-- ===== 地基：审批与预警 =====` 这种），顺序固定（地基表 → 各业务模块 → 初始化数据），保证幂等可重跑（建表用 `IF NOT EXISTS` / 迁移用版本表）。
5. 与"临时文件用完清理"配套：合并进主 SQL 的零散文件用完即清理，不长期留两份。

### 3.6 临时文件 / 一次性代码 清理规则（强制）
1. **临时文件、脚手架脚本、一次性导入/迁移脚本、演示用数据，使用完成后必须清理**，不允许长期留在仓库根目录或 `sql/`、`scripts/` 里"忘了删"。
2. 清理前确认：① 已验证 ② 有价值的内容已沉淀进正式文件（如 DDL 已并入主 SQL、数据已入正式表）③ 无别处依赖。
3. 确需保留的脚本（如"重建索引.py"这类会反复跑的）不进"临时"类，登记进《开发日志》+ 放 `scripts/` 并说明用途；纯临时的一次性文件用完即删（走 Git 历史可追溯，不靠留文件追溯）。
4. 发版前自查：仓库里不该有 `tmp_*`、`临时*.sql`、`test_data_*.csv` 这类残留；发现即清。

### 3.7 文件上传与对象存储（公开/私有两桶，强制分清，2026-10-24 定）

**两个桶，按"是否需要鉴权"分，别混用：**
| 桶 | 权限 | 放什么 | 浏览器怎么显示 |
|---|---|---|---|
| `zhizhun-files`（公开） | 公开读（`mc anonymous set download`） | 给人看的公开图：公司logo、登录背景、员工头像、产品图 | 直接 `<img :src="url">`（MinIO 直链，URL 已是公开地址） |
| `zhizhun-private`（私有） | 私有（`access_policy=0`） | 敏感文件：合同、证件、工资单、内部文档 | 走**代理接口** `GET /resource/oss/private/{ossId}`（带登录token） |

**接口（系统级通用，所有业务模块复用，不重复造轮子）：**
- 上传公开图：`POST /resource/oss/upload`（RuoYi 自带，落公开桶，返回 `url` 直接可用）
- 上传私有文件：`POST /resource/oss/private/upload` → 返回 `{ossId, proxyUrl}`，业务表只存 `ossId`
- 显示/下载私有文件：`<img :src="'/api/resource/oss/private/' + ossId">`（axios 拦截器自动带 token；无 token 返回 401）

**铁律：**
1. 业务模块**只存 `ossId`**，不存直链 URL（私有文件无直链；公开图也建议存 ossId，URL 可由后端拼）。
2. 敏感文件**必须走私有桶**，禁止把合同/证件/工资单传公开桶（等于裸奔）。
3. 两桶的创建/权限在 `scripts/start.sh` 固化（MinIO 容器重启会丢桶设置，每次启动自动确保）。
4. `sys_oss_config` 两条配置：`minio`（公开，access_policy=1）、`minio-private`（私有，access_policy=0）。

### 3.4 基础数据主键规则（强制）
1. **所有基础数据（档案/字典类表：物料、款、工序、岗位、角色、供应商、设备、床位、车位、客户、员工…）必须有唯一的 `id` 主键**（系统生成的稳定唯一键，如自增/雪花/uuid，内部用，不展示）。
2. **每个基础数据同时有一个"编码"字段**（人可读、对外展示），取值方式**二选一，按数据定**：
   - **自填编码**：人工填（如款号、物料编码），需保证唯一（填时校验）。
   - **自动生成编码**：系统按规则生成（如 实裁单号 SCD+日期+类型+流水、包码 PKG 全局流水、设备码 全局流水）。
   - 编码规则、是否可改、改不改历史，随该基础数据定（见《功能命名清单》/ 各模块文档）。
3. **外键一律挂 `id`，不挂"编码"**（编码会变/可回收复用，id 不变，历史数据靠 id 关联——同 地基/员工ID与工号 的原则，推广到所有基础数据）。
4. 编码与 id 的关系：编码是"展示/业务可读"，id 是"系统内部关联"，**两者都存、各司其职**，禁止拿编码当外键。

## 四、代码规范（通用原则，具体语言细则随技术栈落地）

### 4.1 注释规范（强制，不许偷懒）
1. **所有函数/方法、类、模块顶部注释必须中英双语**，中文在前、英文在后，格式固定，不允许只写其中一种语言：
   ```
   # 检查成本差异告警并推送通知
   # Check cost variance alerts and push notifications
   ```
2. 关键业务逻辑块（不是逐行写，但"为什么这么做"必须写）同样中英双语注释。
3. 涉及金额、库存、提成、产能计算的代码，注释必须写明**计算公式**和**边界条件**（如"余料 = 总米数 − 已拉米数，负值按 0 处理"），中英双语。
4. 禁止"复述代码"的废话注释（如 `i += 1  # i加1`）；也禁止业务函数体完全没有注释。
5. 双语注释不是翻译腔堆砌，中文说明业务含义（给本厂开发/维护人员看），英文说明实现要点（给未来可能的协作方/AI 辅助工具看），两者内容有区分度，不是同一句话的机械翻译。

### 4.2 不重复造轮子（强制）
1. 新增任何功能/工具函数前，必须先全局搜索项目内是否已有同类实现，确认没有再写新的。
2. 通用逻辑（分页、权限判断、告警触发、打印模板、编码生成等）必须落在统一的工具/公共服务层，禁止在多个业务模块各写一份。
3. 发现已有第三方库/成熟组件能解决的问题（定时调度、HTTP 客户端、条码生成等），不手写替代实现，引入依赖并记录在文档里。
4. 跨模块复用靠"抽公共层"，不靠"复制粘贴改两个字段"——复制粘贴超过一次即视为重复造轮子，必须重构合并。

### 4.3 命名依据：全系统英文命名以《术语词库索引.md》为准，见其第二节规则

### 4.4 其他通用原则（技术栈确认后细化）
- 变量/函数命名含义明确，禁止无意义单字母（循环变量除外）。
- 错误处理必须显式，禁止静默吞掉异常。
- 配置项（交期准备期、预警阈值、开关）走配置中心/配置表，不硬编码在业务代码里（沿用《生产流程规划.md》"能开关的都不写死"的原则）。

## 五、测试规范

1. 新增业务逻辑必须配对应测试用例，核心成功路径必须有**具体字段值断言**，不能只有"状态码 200/400/500 都算过"这种宽容断言（旧项目质量模块测试长期卡在 30% 覆盖率，根因就是宽容断言，禁止重演）。
2. 涉及金额/库存/提成计算的测试，必须包含**边界用例**（0 件、1 件、最大卷层数、余料为 0、余料反算版长等）。
3. 测试文件/测试函数命名要能直接看出测的是哪个业务点（用中文或对应英文模块名），禁止 `test1`、`test_a` 这种命名。

## 六、Git 规范

### 6.1 分支模型
| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 可发布分支，只接受 PR 合并 | 永久 |
| `dev` | 日常开发集成分支 | 永久 |
| `feat/<中文功能名>` | 单个功能开发 | 合并进 `dev` 后删除 |
| `fix/<中文缺陷名>` | 单个缺陷修复 | 合并进 `dev` 后删除 |

功能名/缺陷名用简短中文描述（可混用拼音首字母/英文缩写），例：`feat/布卷拉布`、`fix/成本告警漏发`。

**多人协作补充约定：**
1. 每个功能任务设一名负责人；参与者各自在独立分支和工作区开发，不共用工作目录。
2. 前后端并行前先确认 API、字段、状态、权限和异常契约；同一迁移批次/共享表只设一名 DDL 负责人。
3. 每个任务按可验收能力拆分，任务说明、责任人、依赖、验收与遗留项按《多人协作与任务交接.md》和《功能任务模板.md》记录。
4. PR 需说明关联需求、行为变化、数据库/配置影响、测试证据和遗留项；合并前完成代码评审与集成验证。
5. `dev` 分支及 PR 流程尚未在当前仓库远端验证建立；团队开始多人协作前由仓库维护者确认远端分支和保护规则，并保持本文与实际设置一致。

### 6.2 提交信息
1. 格式：`<类型>(<范围>): <中文简述>`
   - 类型：`feat`（新功能）/ `fix`（修缺陷）/ `docs`（文档）/ `refactor`（重构，行为不变）/ `test`（测试）/ `chore`（构建/依赖/工程配置）
   - 范围：影响的模块，如 `db`、`cutting`、`approval`、`git`
2. 正文（改动超过 3 行时建议写）用中文说明**为什么**这么改，不是复述 diff。
3. 禁止 `更新`、`修bug`、`tmp`、`wip` 等无信息量提交说明（`wip` 只在本地未整理完的暂存提交允许，推送到远端前必须整理成规范提交）。

**示例：**
```
feat(cutting): 拉布支持多选布卷分层，余料自动回仓
背景：原拉布只能手填布卷号，无法追踪余料，导致库存口径不准
改动：拉布记录表加 物料/层数/余料米数 字段，拉布确认时按实际用量出库，
      余料自动挂回裁剪仓，供下次拉布直接领用
```

### 6.3 提交粒度
1. 一次提交只解决一个问题（一个缺陷 / 一个功能点 / 一次纯格式或文档调整），不混提交。
2. DDL 变更（建表/加列/改索引）单独一次提交，不与业务逻辑改动混提交。
3. 文档（本规范涉及的中文文档）改动单独一次提交，类型用 `docs`。

### 6.4 合并规则
1. `feat/*`、`fix/*` 发起 PR 到 `dev`，至少 1 人 review 后合并；单人团队场景可跳过 review，但**必须自查全量测试通过**再合并。
2. `dev` 合到 `main` 前必须：全量测试通过 + 确认 DDL 迁移已在目标环境执行 + 手动冒烟关键流程。
3. 禁止直接向 `main` push。
4. PR 必须采用《多人协作与任务交接.md》第五节的交接内容；合并完成后负责人更新《功能实现状态.md》和任务记录。

### 6.5 其他
- 不使用 `git reset --hard` 覆盖他人已推提交的公共分支历史。
- 大体积文件（Excel 字典表、图片）不进 Git 主仓库，走 Git LFS 或单独的资料目录管理。

---


### 6.6 提交内容安全规范（强制）
1. **禁止提交任何敏感信息**：账号、密码、手机号、API key/token、私钥等一律不允许出现在 Git 仓库（代码、配置、注释、文档）里。
2. 唯一的例外：**测试环境专用的测试账号/测试密码**可以提交（用于自动化测试/手工联调），但必须：
   - 明确命名/注释标注这是"测试专用账号"，与生产账号区分开；
   - 生产环境账号/密码/token 一律走环境变量或密钥管理工具，不进 Git。
3. 提交前自查（可加入 pre-commit 钩子或用敏感词扫描工具）：搜索 `password`、`pwd`、`token`、`secret`、`api_key` 等关键字，逐一确认不是真实凭据才允许提交。
4. 一旦误提交敏感信息，立即：删除/替换该行 → 用 `git filter-repo` 或 BFG 清理历史 → 通知相关方该凭据已泄露、立即轮换。

## 七、版本记录规范

**定位**：记录"发什么版、包含哪些功能、数据库迁移了什么、已知问题"，是回滚/定位问题的依据，不是逐条开发过程记录（那是开发日志的事，见下一节）。

### 7.1 版本命名
1. 采用"**大版本 + 日期**"粗粒度：`V<major>.<minor>`，例如 `V1.0`、`V1.1`、`V2.0`。
   - `major` 升级：新增独立业务模块（如首次上线"吊挂对接"整个环节）
   - `minor` 升级：既有模块内的功能增强/缺陷修复批次
2. 版本号在发版时定，不预先占号；Git tag 与版本号一一对应（见 6.4）。

### 7.2 版本记录文档（`版本记录.md`，放在 `Docs/` 下）
每个版本一条记录，字段固定：
| 字段 | 说明 |
|---|---|
| 版本号 / 发版日期 | 唯一标识 |
| 对应 Git tag | 可直接 checkout 的回滚点 |
| 本次包含的功能/改动清单 | 功能名（对应《功能命名清单.md》），逐条列出，不写"若干优化"这种模糊描述 |
| 数据库迁移内容 | 本次版本涉及哪些 DDL（建表/加列/改索引），与 6.3 的 DDL 单独提交对应 |
| 已知问题/遗留事项 | 发版时发现但没修的问题、后续要跟进的事项，写清影响范围 |
| 回滚指引 | 出现严重问题如何回退到上一版本（tag 号 + 是否需要人工回滚数据库 DDL） |

### 7.3 触发与责任
1. 每次发版前，开发方更新 `版本记录.md` 对应条目，与发版代码同一批次提交（不允许发完版才补文档）。
2. 发版 = 一条 Git 提交打 tag + 一条版本记录条目，二者必须成对出现，缺一视为发版未完成。

## 八、开发日志规范

**定位**：记录"过程"，给团队内部/后续接手的人看，不是对外交付物。粒度比版本记录细（周级），比 Git commit 粗（做汇总，不逐条抄 commit message）。

### 8.1 开发日志文档（`开发日志.md`，放在 `Docs/` 下）
按**周**为最小单位记录，字段固定：
| 字段 | 说明 |
|---|---|
| 周次 / 日期范围 | 如"2026-10-20 ~ 2026-10-24" |
| 本周推进的功能/任务 | 对应《功能命名清单.md》里的功能名，写清状态（进行中/已完成/被阻塞） |
| 关键决策 | 本周做出的技术方案取舍、与用户核对后定下的规则（引用《生产流程规划.md》章节号），不重复抄需求原文 |
| 遗留/待办 | 本周没做完、被阻塞、需要后续跟进的事，写清阻塞原因（等用户提供清单/等吊挂字典确认等） |

### 8.2 与 Git 的边界
1. 开发日志**不逐条记录每次提交**（那是 `git log` 的事，随时可查），只记录"这一周整体推进了什么、哪些是跨多次提交才能讲清楚的一件事"。
2. 一条"关键决策"若只对应一次 commit，直接写在 commit message 里即可，不必在开发日志里重复；只有需要连续多次提交才完成、或涉及和用户核对过程的决策，才写进开发日志。
3. 开发日志更新频率：跨多次提交的功能或重要决策完成后及时补记；小型单次改动由 Git 提交记录即可。每周检查是否有应补未补的阶段总结，不要求为凑频率重复记录。

## 九、API 文档规范（面向智能体，技术栈无关先定）

1. 每个用户验收通过的功能均须在 `Docs/API/API文档.md` 总索引和功能分组文档登记 API/MCP 契约，并提供对应智能体 Skill；格式遵守《API文档规范.md》。需区分现有 REST 接口、已注册 MCP 工具和仅有设计的工具契约，不得把未接入的 MCP 标成可调用。
2. 每个接口除常规"方法/路径/参数/返回"外，**必须写机器契约四字段**：幂等性、副作用、前置条件、是否需审批——缺一即视为该接口对智能体不可用。
3. 示例请求体必须是可直接运行的 JSON，不允许伪代码。
4. API 文档应以代码路由和可复现的接口实测为依据；路由抽取自动化尚未落地前，维护者需在功能验收时核对接口清单，避免文档漂移。自动化实施时按《API文档规范.md》补充脚本。
5. API 分组名 = 《功能命名清单》里的功能名，一个功能一组，与数据库表名同口径。

## 十、智能体接入规范（内嵌智能体，详见《内嵌智能体规范.md》）

1. 内嵌智能体接管 ERP 的技术路线：**MCP（发现/调用协议）+ 面向动作的 API（能力原子）+ Skill（业务动作编排）**，SDK 这条不建（大模型调用走已定的 OpenAI 兼容接口即可）。
2. **模型网关（LLM/TTS/ASR 三类，均 OpenAI 协议）密钥只进 `.env`**，不进数据库、不进 Git：`.env` 必须进 `.gitignore`，仓库只提交 `.env.example`（占位符模板）；界面只选"用哪套已配置网关"，不提供填 key 入口。
3. **配置红线（防写死）**：任何 LLM/TTS/ASR/Embedding 的 `base_url`、`api_key`、`model`、`维度`、`上下文上限` 一律来自 `.env`，**禁止出现在代码/SQL/文档可运行值里**。换环境/换模型只改 `.env`。提交自查搜 `192.168.`、`http://`、写死的模型名，发现打回。

4. 智能体只通过 MCP 暴露的"工具"操作 ERP，**不允许**直接调用 Web 页面路由或裸 SQL。
5. **权限红线：智能体每次写操作以发起员工本人身份执行、校验、留痕（操作人记工号不记"AI"）；可执行动作集 = 该员工角色权限过滤后的工具集，无权限动作在对话里不出现；禁止开万能/超管代执行口子。**
6. 允许拉开源 agent 框架做内嵌"壳"，但框架只能调我们自定义的 MCP 工具，不得直连数据库、不得绕过权限层（三条选型红线见《内嵌智能体规范.md》第五节）。
7. 一个完整业务动作封装为一个 Skill，步骤顺序锁死，不靠模型临场决定。

## 十一、功能开发与交付流程（在授权范围内主动推进）

**原则：先理解业务，再在明确授权范围内自主完成实现、验证和交付。用户验收后补齐 API/MCP 契约、智能体 Skill 和项目进度；运行时 MCP 尚未接入时如实标记。**

| 步 | 动作 | 产物 | 责任 |
|---|---|---|---|
| 1 | 理解需求、检查关联代码/文档，识别关键业务规则和高风险影响 | 简短分析；复杂功能建立任务单 | 负责人自主完成 |
| 2 | 用户已授权后直接实现；必要时边实现边补齐方案/字段文档 | 可运行代码、DDL、相关文档 | 负责人自主实施 |
| 3 | 执行相关构建、测试、静态检查和开发环境验证，修复授权范围内发现的问题 | 可复核的命令和结果 | 负责人自查 |
| 4 | 提交用户验收；按验收结果迭代 | 验收记录及遗留项 | 用户业务验收 |
| 5 | 验收通过后补齐 API/MCP 文档、智能体 Skill、功能状态和开发进度；未接入能力须标清状态 | 完整交付记录 | 负责人收尾 |

**必须暂停并请用户决策的情况：**业务目标或关键规则存在多种会改变业务结果的解释；需要扩大到未授权模块；需要改变权限、安全或审批规则；会改变既有数据含义或造成重要数据不可逆影响；生产环境迁移/部署；或需要产生明显外部成本。说明具体影响并提出推荐方案。一般字段实现、数据库设计细节、校验、索引、代码结构和开发环境迁移属于已授权功能的正常工程工作，由负责人自主完成，不重复请求逐项审批。

- 用户提出实施请求或确认实施计划后，不得仅因任务单字段尚未逐项填写、实现确认单未单独签字或非关键细节待定而停在计划阶段。负责人应采用与既有业务约定一致、风险最低的合理方案继续，并记录假设。
- 用户验收前可以完成代码、构建、开发环境迁移和可逆的开发数据操作；生产部署及重要数据破坏性操作按上文暂停确认。
- 未验收的接口不得标成已验收的机器契约。运行时 MCP 工具和业务动作 API 尚未实现时，可形成契约草案，但须注明未接入/不可调用。
- API 文档格式/机器契约和智能体安全红线见《API文档规范.md》《内嵌智能体规范.md》。

## 十三、前后端 bigint 传输铁律（2026-10-27 定，已踩三坑）

1. **前端一律以字符串传输 bigint id**（orgId/postId/roleId/userId/groupId——JS number>2^53 丢精度）；**禁止 `Number(id)`/`map(Number)`**。
2. **后端入口统一转换**：`Long.valueOf(str)` / 专用 helper（如 PersonController 的 `orgIdOrNull`）；**禁止 `instanceof Number` 判断**（前端来的都是字符串，恒 false——岗位精度、部门落库、小组回显三个 bug 全是这两类写法）。
3. Java Long(64位)无精度问题，转换后正常用；SQL 参数传 Long 不传 String（PG bigint 列拒 varchar）。
