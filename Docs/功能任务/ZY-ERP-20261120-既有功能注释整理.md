# 既有功能注释整理

## 一、目标与范围

- 统一文件头写法，记录功能目的、设计思路、实现方法、依赖与引用路径、责任人、修改标记和真实测试状态。
- 梳理现有自研业务代码和本项目改造过的框架代码，覆盖 REST API、MCP 工具、智能体/文件处理接入、前端页面、数据库迁移、运行脚本、配置及直接关联的辅助代码。
- 本次范围按实际代码追踪：`frontend/src/`、`RuoYi-Vue-Plus/ruoyi-admin/src/main/java/org/dromara/web/`、`RuoYi-Vue-Plus/ruoyi-extend/ruoyi-snailai-server/`、项目根目录 `sql/` 与 `scripts/`，以及已改造的 RuoYi/Warm-Flow/Spring AI Alibaba 对应文件。
- 自动生成代码/资源、依赖锁文件、未改造的第三方源码、两份 XLSX 及其伴随说明文件不属于代码注释改造范围。
- 每个承担业务含义的逻辑段都要说明处理目的和业务约束；非直观或高风险语句按需逐行解释，注释长度不设上限。
- 保持所有现有业务规则、权限、数据契约、接口行为和数据库行为不变。

## 二、注释要求

- 文件头回答“做什么、为什么这样设计、如何实现、依赖或引用什么”。引用使用项目内相对路径。
- 类/组件/模块注释说明职责和主要边界；方法/函数注释说明业务输入、输出、状态变化、副作用和调用条件。
- 逻辑块注释说明业务判断、数据流转、事务/并发/幂等、权限/审计、异常和特殊边界。
- 评论必须与代码一致。不得编造历史测试结论；本次未运行的业务测试继续明确标为未执行。

## 三、验收范围

- 文件头字段完整；自研文件按已确认的项目人员信息登记；对上游框架文件只标注实际项目改造责任并保留原版权信息。
- API、MCP、审批、智能体文件注释能够解释调用契约、身份权限、数据范围和副作用。
- 注释整理不引入业务逻辑差异；严格 JSON、二进制、自动生成产物按开发规范的格式例外处理。
- 推送代码前完成差异检查、注释范围核对和当前分支/远端状态核对。
