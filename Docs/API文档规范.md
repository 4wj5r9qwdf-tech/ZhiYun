# API 文档规范（面向智能体接入）

> 版本：v1
> 更新日期：2026-11-04
> 说明：本文档规定每个已验收功能的 API/MCP 契约文档与智能体 Skill 格式。它不把普通 Web REST 接口误称为已注册 MCP 工具；必须分别记录接口实现状态和智能体运行时接入状态。与《开发规范.md》《功能命名清单.md》《生产流程规划.md》配套使用。

---

## 一、定位与原则

1. **服务对象是智能体**：API 文档要让"一个不读懂页面、只能看 JSON 契约的模型"能独立理解业务动作。人读是次要的；若 MCP 运行时尚未接入，必须明确标记不可调用。
2. **与现有 Web 页面路由分开**：面向智能体的 API 是"动词式能力接口"（查询库存、开裁剪单、报工），字段为"机器调用"设计（参数清晰、返回结构化、幂等可控），**不复用** Jinja2 页面渲染时那些"给人看"的端点。
3. **按《功能命名清单》的模块分组**：一个功能一组 API，组名=功能中文名+英文名（如"裁剪构成单 cut_order"）。
4. **文档与代码同源**：文档以实际路由和接口实测为依据。路由自动抽取脚本尚未落地前，在功能验收时人工核对代码与实测结果，避免纯凭记忆维护。

## 二、每个 API 必须写的字段（固定模板）

每个接口按下面结构记录，缺字段的接口视为**未达标，智能体不可用**：

### 基本契约
| 字段 | 说明 |
|---|---|
| 功能分组 | 属于哪个功能（对应《功能命名清单》） |
| 方法 + 路径 | 如 `POST /api/v1/cut_order/create` |
| 一句话说明 | 这个接口做什么（中文） |
| 读/写类型 | **只读**（query）或 **写**（mutation）——必填，智能体据此判断副作用 |

### 请求参数
| 字段 | 说明 |
|---|---|
| 参数表 | 每个参数：名称 / 类型 / 必填 / 默认值 / 说明（中英双语，与代码注释一致） |
| 嵌套结构 | 含对象/数组的参数必须展开列出内部字段 |
| 示例请求体 | **可直接运行的 JSON 示例**，非伪代码，必填/可选字段都露出来 |

### 返回
| 字段 | 说明 |
|---|---|
| 成功返回示例 | 完整 JSON，含所有字段（哪怕值为 null 也要列出） |
| 错误返回 | 每种可预期错误的错误码 + 触发条件 + 示例 |
| 返回字段说明 | 关键字段逐条注明含义（尤其金额单位、数量单位、状态枚举取值） |

### 机器契约（智能体专用，强制）
| 字段 | 说明 |
|---|---|
| 幂等性 | 该接口**重复调用**是否产生副作用。写操作必须声明：支持幂等键（哪个字段）/ 不支持（重试会重复扣库存等风险） |
| 副作用 | 调用后会改变哪些数据/触发哪些联动（如"生成打码单""扣减布卷库存"） |
| 前置条件 | 调用前必须满足什么（如"该实裁单已确认""物料已入库"） |
| 是否需审批 | 该动作是否挂在审批流上（对应审批引擎回调） |
| 权限要求 | 该动作需要哪个角色/权限码才能执行（对应 sys_role 权限模型）；智能体按发起员工权限过滤，无权限则不可见/不可执行 |

## 三、文档组织（文件结构，随技术栈落地）

> **目录约定（2026-10-26 定，2026-11-04 更新）：API 文档进 `Docs/API/`；功能验收后在 `Docs/Skills/<功能名>/SKILL.md` 提供智能体 Skill。**

1. **总索引**：`Docs/API/API文档.md`（总纲）——所有功能分组清单 + 每个接口一行速查（方法/路径/说明/读写），供智能体先定位再细看。
2. **分组文档**：每个功能一份，放 `Docs/API/` 下，文件名 = 功能中文名 + `API`，如 `Docs/API/建筑档案API.md`。组内按"只读接口在前、写接口在后"排列。
3. **示例请求体统一放可运行代码块**（语言标注），智能体可直接复制执行验证。

## 四、与智能体接入方式的关系（SDK / API / Skill / MCP）

| 手段 | 在 ERP 场景的作用 | 是否建设 |
|---|---|---|
| **MCP** | 智能体发现/调用 ERP 能力的协议入口，把能力暴露为工具；智能体不直接碰后端 Web 路由 | 每个已验收功能都记录工具映射与接入状态；运行时实现可分批接入 |
| **面向动作的 API** | 能力原子（查询/开单/报工），字段为机器调用设计，与 Web 页面 API 分开 | 每个已验收功能记录现有 REST 路由及 agent API 状态；不足时标明待建设 |
| **Skill** | 一个完整业务动作的多步编排，按确定步骤调用能力 | 每个已验收功能都交付 Skill；依赖工具未接入时标注草案/不可执行 |
| **SDK** | 调大模型那段（OpenAI 兼容 `/v1/chat/completions`）的封装，不碰 ERP 业务 | **基本不需要**，除非绑定某家 Agent 框架 |

**目标架构：智能体接管 ERP 时，可由 MCP（发现/调用）+ 面向动作的 API（能力原子）+ Skill（业务动作编排）协作；这描述目标形态，不表示所有 ERP 功能当前都必须建设这套能力。** SDK 不作为默认建设项，除非选定框架确有需要。具体批次按用户确认范围实施。

## 五、落地节奏

1. 本文档规定已验收功能的 API/MCP 契约和 Skill 格式；未接入运行时的契约须清楚注明状态。
2. 功能验收时核对实际路由和请求响应；待 API 数量和维护成本需要时，再实现"路由表 → API 文档"自动抽取脚本。
3. 人工在骨架上补"机器契约"四字段（幂等/副作用/前置/审批），这是脚本抽不出来的，只能按业务逻辑人工填。
4. 功能验收后必须交付 Skill 与 MCP 工具映射契约；MCP server 及工具运行时接入按项目集成批次实施，未接入前 Skill 标为草案/不可执行。
6. 参数/字段英文名一律以《术语词库索引.md》既定词为准，不自造；释义列可直接取词库释义做底稿。
